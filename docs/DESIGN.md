## 3. Стани

### 3.1 Глобальний етап квесту (FR-24)

```
DRAFT ──/open_reg──▶ REGISTRATION ──/start_quest──▶ RUNNING ──/close_quest──▶ CLOSED ──/publish_results──▶ RESULTS
                         ▲    │                       │  ▲
                         └────┘ /close_reg, /open_reg  └──┘ (реєстрацію можна відкривати/закривати незалежно)
```

- Етап і прапорець `registration_open` зберігаються в таблиці `game_state` (один рядок).
- `REGISTRATION`: можна зареєструватися, але кнопка «Почати квест» неактивна («чекаємо старту від ведучого»).
- `RUNNING`: зареєстровані бачать «Почати». Тим, хто зареєструвався й чекав, бот **розсилає** повідомлення «Квест стартував!» з кнопкою.
- `/close_quest`: усі незавершені спроби → `CLOSED_UNFINISHED`, нарахування зупиняється, бот повідомляє й видає промокод (FR-19, FR-22).
- Перехід у `RUNNING` блокується, якщо `content.has_todo` (FR-30). `/start_quest force` стартує попри TODO.
- Кожен перехід бот просить підтвердити кнопками ✅/❌.

### 3.2 Учасник (FSM aiogram + дзеркало в БД)

```
/start ─▶ [закрито?] ─▶ AWAIT_CODE ─▶ AWAIT_NAME ─▶ AWAIT_STATUS ─▶ (AWAIT_COURSE) ─▶ REGISTERED
                                                                                       │ (етап RUNNING)
                                                                                       ▼
                                   ROUND_INTRO(r) ◀──────── кінець раунду ────── QUESTION(r,q)
                                        │ «Почати раунд»                              ▲  │ відповідь / таймаут
                                        └──────────────────────────────────────────────┘  ▼
                                                                                    FINISHED ─▶ AWAIT_FEEDBACK ─▶ DONE
```

- **Справжнє джерело правди — таблиця `attempts`, а не FSM aiogram.** FSM-сховище (теж у Postgres або Redis) використовується лише для кроків реєстрації. Ігровий стан завжди читається з `attempts`, тому рестарт не ламає гру (FR-13, NFR-1).
- Deep link `/start <code>` одразу пропускає крок AWAIT_CODE.
- Якщо користувач, який уже зареєструвався, натисне `/start`, бот поверне його туди, де він зупинився (картка раунду або **повторне надсилання поточного питання** з тим самим дедлайном).
- Будь-який текст під час гри → «Обери відповідь кнопкою 👆».

## 4. Модель даних

```sql
game_state (            -- рівно один рядок, id = 1
  id               int PK,
  phase            text,          -- DRAFT|REGISTRATION|RUNNING|CLOSED|RESULTS
  registration_open bool,
  access_code      text,          -- порівнюємо case-insensitive, trim
  started_at       timestamptz,
  closes_at        timestamptz,   -- необов'язково: плановий час закриття (для «лишилось N хв»)
  closed_at        timestamptz,
  content_hash     text           -- хеш quest.yaml на момент старту (захист від правок посеред гри)
)

users (
  tg_id        bigint PK,
  username     text NULL,
  tg_name      text,              -- first+last з Telegram
  full_name    text NULL,         -- введене при реєстрації
  status       text NULL,         -- FIT_STUDENT|APPLICANT|OTHER_STUDENT|OTHER
  course       text NULL,         -- 1|2|3|4|MASTER
  registered_at timestamptz NULL,
  is_admin     bool default false,
  excluded     bool default false, -- не в рейтингу (FR-16)
  blocked_bot  bool default false  -- ставимо, якщо отримали 403 при надсиланні
)

attempts (
  id               bigserial PK,
  tg_id            bigint UNIQUE REFERENCES users,   -- одна спроба (FR-6)
  status           text,     -- ROUND_INTRO|QUESTION|FINISHED|CLOSED_UNFINISHED
  started_at       timestamptz,
  finished_at      timestamptz NULL,
  plan             jsonb,    -- персональний порядок: [{qid, option_order:[2,0,3,1]}...]
  cursor           int,      -- індекс у plan (поточне питання)
  q_sent_at        timestamptz NULL,   -- коли надіслано поточне питання
  q_deadline       timestamptz NULL,   -- q_sent_at + limit
  q_message_id     bigint NULL,        -- щоб прибрати клавіатуру
  score            int default 0,
  total_time_ms    bigint default 0,
  promo_sent       bool default false,
  results_sent     bool default false,
  feedback         text NULL
)

answers (
  attempt_id   bigint REFERENCES attempts,
  qid          text,
  chosen       int NULL,     -- індекс варіанта в ОРИГІНАЛЬНОМУ порядку з yaml; NULL = таймаут
  is_correct   bool,
  response_ms  int,
  answered_at  timestamptz,
  PRIMARY KEY (attempt_id, qid)       -- захист від подвійного зарахування (NFR-4)
)

media_cache (
  path       text PK,      -- content/images/xxx.png
  sha256     text,         -- змінився файл → перезавантажити
  file_id    text
)
```

Питання **в БД не зберігаємо**: вони в `quest.yaml` і завантажуються в пам'ять при старті. `answers.qid` посилається на `id` питання з yaml.

## 5. Формат контенту (`content/quest.yaml`)

```yaml
meta:
  title: "IT-квест до Дня ФІТ"
  promo: { code: "HILLEL1000", text: "..." }
  defaults: { time_limit: 20, shuffle_options: true, shuffle_questions: false }

rounds:
  - id: r1
    title: "IT Quizlet"
    intro: "Текст картки раунду"
    time_limit: 20                # секунд на питання
    shuffle_options: true
    shuffle_questions: false
    sections:                     # раунд може мати кілька підблоків зі своїм інтро (раунд 5)
      - id: r1s1
        intro: null
        question_type: choice     # choice | binary
        labels: null              # для binary: ["✅ Правда", "❌ Брехня"]
        questions:
          - id: r1q01
            text: "..."
            image: null           # шлях від content/
            options: ["...", "...", "...", "..."]   # лише для choice
            correct: 1            # індекс (choice) або індекс мітки (binary)
            explanation: "..."    # показується в розборі після публікації результатів
            todo: null            # рядок = позначка «не готово» → валідатор попередить
```

**Правила валідатора:**
- `id` питань і раундів унікальні;
- для `choice` має бути 2–4 варіанти, `correct` у межах;
- для `binary` у секції задано `labels` (рівно 2);
- `image` існує на диску;
- текст питання + варіанти вкладаються в 1024 символи, якщо є картинка (ліміт підпису Telegram), або в 4096, якщо немає;
- будь-яке непорожнє `todo`, `correct: null` чи рядок, що починається з `TODO`, рахується як незаповнене → список виводять `/validate` і стартовий лог.

## 6. Ігровий цикл (ядро `services/game.py`)

### 6.1 Старт спроби
1. Перевірити, що етап `RUNNING` і в користувача ще немає спроби.
2. Згенерувати `plan`: для кожного раунду (по порядку) секції по порядку, питання (перемішані, якщо `shuffle_questions`), для `choice` — випадкова перестановка варіантів, якщо `shuffle_options`.
3. Вставити `attempts` (`UNIQUE tg_id` захищає від подвійного старту), `status=ROUND_INTRO`, `cursor=0`.
4. Показати картку раунду 1.

### 6.2 Картка раунду / секції
Повідомлення: назва, правила, «N питань, M с на кожне», кнопка **«▶️ Почати раунд»** (`callback: go:{cursor}`). Час на картці не рахується.

### 6.3 Надсилання питання
1. Взяти `plan[cursor]`. Сформувати повідомлення:
   - **choice:** текст питання, нижче варіанти `A) … B) …` у персональному порядку; кнопки `A B C D` в один ряд. *Варіанти завжди в тексті, на кнопках лише літери*, бо Telegram обрізає довгі підписи кнопок (промпти, описи).
   - **binary:** текст (або підпис до картинки) + 2 кнопки з `labels`.
   - Шапка: `Раунд 3/5 · Питання 4/10 · ⏱ 15 с`.
2. Надіслати (з картинкою через кешований `file_id`). **Якщо підпис з картинкою > 1024 символів** (наприклад, `r5g01` з чотирма довгими промптами — ~1030 символів), бот надсилає картинку окремим повідомленням, а питання з варіантами й кнопками — наступним. Таймер стартує з другого повідомлення.
3. **Атомарно** записати `q_sent_at = now()`, `q_deadline`, `q_message_id`, `status=QUESTION`.
4. Запланувати таймер на `q_deadline` (§7).

### 6.4 Прийом відповіді (`callback: a:{cursor}:{btn}`)
```
UPDATE attempts SET cursor = cursor + 1, status = '…'
WHERE id = :id AND cursor = :cursor AND status = 'QUESTION'
RETURNING …
```
- 0 рядків → відповідь застаріла або дубль → `answerCallbackQuery("Відповідь уже зараховано")` і вихід. **Це головний механізм ідемпотентності** (NFR-4).
- `elapsed = now - q_sent_at`. Якщо `elapsed > limit + 1.5 с` → зараховуємо як таймаут.
- Перевести `btn` → індекс в оригінальному порядку → `is_correct`.
- Вставити `answers`, оновити `score`, `total_time_ms += min(elapsed, limit)`.
- Скасувати таймер. Відредагувати попереднє повідомлення: прибрати клавіатуру й дописати «✅ Відповідь прийнято» (без правильності, FR-12).
- Далі: наступне питання / картка наступної секції чи раунду / фініш.
- Усе це в **одній транзакції**, крім викликів Telegram API (вони після коміту).

### 6.5 Таймаут
Робить те саме, що §6.4, з `chosen=NULL`, `response_ms=limit` і такою самою перевіркою `cursor`. Повідомлення редагується на «⏰ Час вийшов», далі бот надсилає наступне питання.

### 6.6 Фініш
1. `status=FINISHED`, `finished_at=now()`.
2. Повідомлення: «🎉 Ти пройшов квест! Твій результат: X з Y. Місця оголосимо в Zoom».
3. Промокод Hillel (`promo_sent=true`), згадка партнерів і призів.
4. Запит відгуку: «Одне речення: як тобі квест?» з кнопкою «Пропустити». Текст іде в `attempts.feedback` (до 300 символів).

### 6.7 Закриття квесту (`/close_quest`)
Для всіх спроб у `ROUND_INTRO`/`QUESTION`: `status=CLOSED_UNFINISHED` атомарно, скасувати таймери, прибрати клавіатуру з поточного питання. Розіслати повідомлення «Квест закрито, зараховано N відповідей» + промокод (§9).

### 6.8 Публікація результатів (`/publish_results`)
Кожному учаснику з рейтингу: «Твоє місце: 12 з 143, бал 41/55». Далі розбір: усі питання, ✅/❌, правильна відповідь і `explanation`. Розбір розбиваємо на кілька повідомлень до 4096 символів, розсилаємо через broadcast-чергу.

## 7. Таймери й відновлення

- В пам'яті: `dict[attempt_id] -> asyncio.TimerHandle` (через `loop.call_at`), при спрацюванні викликається `game.on_timeout(attempt_id, cursor)`.
- **Сервер — джерело правди**, таймер лише «будильник». Навіть якщо таймер загубиться, відповідь, що прийде після дедлайну, все одно стане таймаутом (§6.4).
- **Recovery при старті:** `SELECT * FROM attempts WHERE status='QUESTION'`. Для кожної: якщо `q_deadline` минув — одразу `on_timeout`, інакше запланувати таймер. Учасник, що застряг посеред питання, побачить «⏰ Час вийшов» і наступне питання.
- **Сторож:** раз на 5 с фонова задача шукає `status='QUESTION' AND q_deadline < now() - 3s` (на випадок, якщо таймер загубився) і закриває такі питання.
- Видимий таймер **не редагуємо щосекунди**: це спалить ліміти Telegram. У шапці показуємо `⏱ 20 с`, цього достатньо.

## 8. Медіа (NFR-6)

- `scripts/prepare_images.py`: усі картинки → JPEG, 1280 px по ширині, якість 85, **однакове співвідношення сторін для раунду «Справжнє чи ШІ»**, щоб відповідь не видавали розмір чи якість (див. TODO).
- Команда `/warmup` (адмін): бот надсилає кожну картинку адміну, зберігає `file_id` у `media_cache` (за `sha256`). Під час гри картинки йдуть лише через `file_id`, тож надсилання миттєве.
- Якщо `file_id` немає (забули warmup), бот завантажує файл і кешує на льоту.

## 9. Розсилки й ліміти Telegram

- Ліміт Telegram ~30 повідомлень/с на бота, 1 повідомлення/с в одному чаті.
- `services/broadcast.py`: черга з токен-бакетом **25 повідомлень/с**, retry на `RetryAfter`, на `Forbidden` ставимо `users.blocked_bot=true`.
- Через чергу йдуть масові події: «Квест стартував», закриття, результати, `/broadcast`.
- Звичайний ігровий трафік (відповідь на натискання) йде напряму: кожен учасник генерує < 1 повідомлення/с, а 200 людей з середнім темпом ~1 відповідь на 8 с дають ~25 повідомлень/с. Це на межі, тому **throttling-middleware** відкидає натискання частіше ніж раз на 0,5 с від одного користувача.

## 11. Живе табло (FR-27)

- `GET /board?token=…` — HTML-сторінка у стилі ФІТ, розрахована на показ екрана в Zoom (великий шрифт, темна тема).
- Вміст: великі лічильники (зареєстровано / грає / завершили), топ-10 (ім'я, бал, час), таймер до закриття, якщо `closes_at` задано.
- `GET /api/board?token=…` повертає JSON, сторінка опитує його кожні 3 с.
- Порт 8080, у compose проброшено як `127.0.0.1:8080` + nginx/Caddy з HTTPS, **або** просто `0.0.0.0:8080` із довгим токеном. Обираємо при деплої.
- Імена в публічному табло скорочуємо: «Ім'я П.».

## 12. Тексти, що бачить учасник

Системні тексти лежать у `bot/texts.py` (або в `quest.yaml → messages`, щоб їх можна було правити без коду, **так краще**):
- привітання, запит коду, «реєстрацію ще не відкрито», «невірний код»;
- згода (FR-5);
- «чекаємо старту», «квест стартував»;
- правила гри (показуються перед раундом 1);
- фінальне повідомлення + партнери + промокод;
- «квест закрито», результати.

Тон: дружній, з емодзі, як у пості-анонсі.

## 13. Безпека й крайові випадки

| Ситуація | Поведінка |
|---|---|
| Подвійне натискання / натискання на старе питання | CAS по `cursor` → «вже зараховано» |
| Натискання й таймер спрацювали одночасно | Те саме: виграє тільки той, хто перший змінив `cursor` |
| Учасник видалив чат / заблокував бота | `blocked_bot=true`, таймери далі закривають питання, спроба доходить до кінця з нулями |
| Рестарт бота посеред гри | Recovery (§7) |
| Хтось грає з другого акаунта | Не відстежуємо; адмін може зробити `/exclude` за потреби |
| Хтось вводить чужий код / підбирає код | Ліміт 5 спроб на хвилину на користувача |
| Хтось пише текст під час гри | Підказка «обирай кнопкою» |
| Правка `quest.yaml` під час RUNNING | `/reload_content` відмовляє, якщо змінились `id`/кількість питань |
| Ім'я з посиланнями чи непристойне | Обрізаємо до 60 символів, прибираємо `@` і URL; адмін може `/exclude` |
